Flujo Geosupport - Imagenes PAO

Documento funcional de la solucion de imagenes PAO: preparacion de rutas, carga al datastore y mosaico, actualizacion de geometrias, normalizacion Rasterio y preparacion del APRX.

01Paths datastore 02Carga mosaico 03Footprints indice 04Normalizacion 05APRX publicacion

Vision General

El flujo convierte una entrega nueva de imagenes drone en informacion lista para consumo SIG. La solucion relaciona cada archivo con una fecha, un sector geografico, una ruta definitiva en el datastore, un registro en el mosaic dataset, un footprint en la capa de indice y una capa raster organizada en el APRX de publicacion.

Entrada confiable La carpeta recibida se considera una entrega valida de imagenes nuevas. La validacion se centra en fecha, cruce espacial, destino y compatibilidad con el modelo PAO.
Nombre final El nombre destino se crea con fecha + sector: CL_MLP_PAO_IF_Ortho_YY_MM_DD_Sector.tif.
Trazabilidad Cada imagen mantiene relacion entre path origen, path destino, atributos del mosaico, footprint de indice y capa de visualizacion en APRX.

Secuencia funcional

  1. Determinar nombre final y path de datastore para cada imagen nueva.
  2. Copiar la imagen al datastore, cargarla al mosaic dataset y poblar atributos criticos.
  3. Exportar footprints del mosaico, homologar campos y anexar las geometrias al indice de vuelos.
  4. Normalizar las imagenes con Rasterio usando el footprint como mascara de recorte limpia.
  5. Preparar el APRX con las imagenes como capas raster referenciadas fuera del image server.
01

Preparar paths destino para datastore

Esta etapa define como debe llamarse cada imagen y donde debe quedar dentro del datastore. El nombre original solo aporta la fecha cuando esta disponible; el sector no se infiere desde texto, se calcula por cruce espacial.

ElementoParticipacion en el flujo
Carpeta de imagenes nuevasOrigen de los TIF/TIFF que se incorporaran al proceso.
Diccionario de fechasflujo_geosupport_etapas/json/fechas.json. Resuelve casos donde el nombre de archivo no trae una fecha confiable.
Feature class de sectoresPoligonos del indice de vuelos PAO usados para determinar el sector por interseccion espacial.
Sensor excluidoLa regla principal excluye DJI MATRICE 350 RTK; si una imagen no cruza, se intenta una segunda busqueda contra ese sensor.
Datastore destinoRaiz corporativa donde se arma la ruta final: carpeta por sector, carpeta mensual y nombre normalizado.

Reglas de nombre y destino

  • La fecha se toma del nombre de archivo o del diccionario JSON cuando existe una regla explicita.
  • El sector se toma del poligono con mayor participacion espacial sobre la imagen.
  • El nombre del sector se preserva tal como esta en la capa, sustituyendo espacios por guion bajo para el nombre de archivo.
  • El resultado de nombre es CL_MLP_PAO_IF_Ortho_YY_MM_DD_Sector.tif.
  • Las imagenes sin fecha, sin cruce espacial o sin carpeta destino quedan separadas para revision.
  • Los casos sin cruce generan un rectangulo de extent en una GDB de revision visual, con el path de la imagen como atributo.
La importancia de la fecha es que participa directamente en el nombre final, en la carpeta mensual y en los atributos posteriores. Si la fecha no esta en el nombre, debe existir en una tabla o en el diccionario JSON.
02

Cargar datastore y mosaic dataset

Esta etapa materializa la imagen en su ubicacion definitiva, la registra en el mosaic dataset y actualiza los campos que permiten consultar, publicar y mantener la informacion cargada.

ElementoParticipacion en el flujo
Manifest de pathsLista de imagenes listas con path origen, path destino, fecha, sector y atributos derivados.
DatastoreRepositorio fisico donde queda el TIF final, usando la nomenclatura PAO.
Mosaic datasetDataset ArcGIS donde se registra cada raster para uso como image service.
Footprint del mosaicoGeometria operativa generada despues de agregar el raster, usada como base para el indice y la normalizacion.

Metodo de carga

  • La imagen se copia desde la carpeta de entrega hacia su path definitivo en el datastore.
  • El raster del datastore se incorpora al mosaic dataset con AddRastersToMosaicDataset.
  • El footprint se recalcula con BuildFootprints para representar la cobertura real del raster.
  • El registro del mosaico queda identificado por su OBJECTID.

Mapeo de campos criticos

  • Sector: sector resultante del cruce espacial.
  • FechaAdqui / Fecha_Adqui: fecha de adquisicion derivada del nombre o diccionario.
  • FechaCarga / Fecha_Publ: fecha de publicacion/carga.
  • URL: ruta o URL construida con la logica PAO del datastore.
  • Proyecto: valor fijo PAO.
  • Sensor: valor fijo DJI Mavic Enterprise para las imagenes del flujo.
  • MaxPS: 10000, LowPS: 0.15, MinPS: 0.
  • ProductName / ProductNam: toma el OBJECTID del registro del mosaico.
03

Actualizar footprints en indice de vuelos

El indice de vuelos PAO necesita recibir las geometrias de las imagenes nuevas para que la solucion territorial pueda consultar y publicar cada cobertura. La geometria fuente es el footprint ya calculado en el mosaic dataset.

ElementoParticipacion en el flujo
Mosaic datasetFuente desde la que se exportan las geometrias footprint de las imagenes cargadas.
GDB temporalEspacio intermedio donde se prepara el esquema antes de anexar al indice definitivo.
Feature class indiceCapa corporativa CL_MLP_PAO_Indice_Vuelos_PAO_IMGS_PO, donde quedan las geometrias consultables.

Homologacion de campos

  • FechaAdqui se transforma a Fecha_Adqu.
  • FechaCarga se transforma a Fecha_Publ.
  • NombreVuelo se transforma a Nombre_de_Vuelo.
  • ProductName se transforma a ProductNam.

Nombre de vuelo

  • Despues del append, el campo Nombre_de_Vuelo se recalcula para los registros con sector y fecha.
  • El formato es NNN_yy_mm_dd_sector.
  • La secuencia se genera ordenando por Name ASC, manteniendo un identificador legible y consistente.
04

Normalizar imagenes con Rasterio

La normalizacion limpia las imagenes usando el footprint como mascara. Se usa Rasterio porque permite controlar el recorte, las bandas, la transparencia y la escritura GeoTIFF sin deformar la imagen.

ElementoParticipacion en el flujo
Raster del datastoreImagen ya copiada y registrada en el mosaico.
FootprintPoligono usado como limite de mascara para mantener solo el area valida.
RasterioMotor de recorte y escritura para generar una salida RGB/alpha compatible con ArcGIS.

Reglas de normalizacion

  • El recorte usa rasterio.mask.mask con crop=True.
  • Si el raster es RGB, se preservan sus tres primeras bandas.
  • Si el raster viene como una banda con colormap, se convierte a RGB completo.
  • Se agrega banda alpha para dejar transparencia fuera del footprint.
  • La salida mantiene georreferenciacion, resolucion y visualizacion compatible con ArcGIS Pro e image service.
El objetivo no es cambiar el contenido visual de la imagen, sino dejar una version limpia dentro del poligono valido y evitar bordes o fondos no deseados.
05

Preparar APRX para publicacion

La publicacion tambien requiere que las imagenes nuevas puedan revisarse como capas raster referenciadas en el APRX. Esta etapa organiza esas capas dentro de la estructura visual existente.

ElementoParticipacion en el flujo
APRX operativoProyecto ArcGIS Pro usado para preparar la visualizacion PAO.
Mapa destinoCL MLP PAO 27 Imagenes Aereas PAO Image Server.
Grupo destinoVuelos Drone PAO > Imagenes Drone.
Capas rasterImagenes del datastore agregadas como capas directas, no como parte del image server.

Reglas APRX

  • Las imagenes nuevas se agregan al grupo existente Imagenes Drone.
  • Se evita duplicar capas cuando ya existe una equivalencia por nombre.
  • El renombrado remueve CL_MLP_PAO_IF_Ortho_, tmp_ y la extension .tif.
  • El orden visual queda de la imagen mas nueva a la mas antigua usando la fecha contenida en el nombre.
  • La estructura del grupo Vuelos Drone PAO se preserva para mantener consistencia con el APRX historico.
Documento funcional asociado al flujo Geosupport PAO. Mantener sincronizado cuando cambien reglas de negocio, campos criticos, rutas corporativas, sensores o criterios de normalizacion.
