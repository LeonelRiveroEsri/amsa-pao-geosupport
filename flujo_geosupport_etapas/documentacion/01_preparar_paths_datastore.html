01 - Preparar paths destino para datastore

Informe funcional de la primera etapa del flujo Geosupport para nuevas imagenes PAO. El objetivo es preparar el manifiesto de rutas destino antes de copiar archivos o cargar el mosaico.

Objetivo

Esta etapa recibe una carpeta con imagenes nuevas y genera la lista oficial de salida para el datastore: origen, nombre final, carpeta destino, carpeta mensual y path completo de destino. La etapa no modifica el datastore ni el mosaic dataset.

Se asume que las imagenes recibidas en la carpeta de entrada son las imagenes que se quieren procesar. En esta etapa no se valida si ya fueron cargadas antes en el mosaico, no se comparan contra inventarios historicos y no se ejecutan controles de duplicidad contra el mosaic dataset. La revision se concentra en preparar correctamente el destino esperado para la siguiente etapa.

Entrada

Entrada Descripcion Uso en el flujo
PATH_INPUT_IMAGENES Carpeta raiz donde llegan las imagenes nuevas del vuelo. Se recorre de forma recursiva, incluyendo subdirectorios.
json/fechas.json Diccionario opcional de fechas por nombre de archivo. Tiene prioridad sobre la fecha detectada desde el nombre. Permite procesar archivos sin patron de fecha o con nombres no estandar.
PATH_FC_INDICE_VUELOS_IMGS Feature class con geometria de sectores o footprints de referencia. Define el sector geografico que se usara en el nombre final de la imagen.
PATH_DATASTORE_DESTINO_RAIZ Raiz del datastore de imagenes PAO. Se combina con carpeta por sector, carpeta mensual y nombre final.
QUERY_INDICE_VUELOS Filtro aplicado al feature class de sectores. Permite excluir registros que no corresponden a este flujo, por ejemplo otro sensor.

Secuencia del flujo

1. Buscar imagenes Se leen los archivos dentro de la carpeta input y todos sus subdirectorios.
2. Filtrar ortomosaicos Para preparar carga al mosaico se consideran solo archivos .tif y .tiff.
3. Cruzar espacialmente Cada imagen se cruza contra el feature class de sectores para definir el sector dominante.
4. Construir destino Se genera nombre final, carpeta mensual y path completo en el datastore.

Reglas de negocio

Busqueda de imagenes

  • La busqueda es recursiva desde PATH_INPUT_IMAGENES.
  • El manifest conserva el path original y el path relativo dentro de la carpeta de entrada.
  • Para esta etapa se preparan archivos .tif y .tiff; otros formatos pueden aparecer en el inventario inicial, pero no pasan como imagenes listas para mosaico.

Fecha de adquisicion

  • Primero se busca la fecha en json/fechas.json, usando el nombre normalizado del archivo o el codigo GEOSP-TRN.
  • Si el archivo no esta en el diccionario, la fecha se obtiene desde el string del nombre original de la imagen.
  • La fecha se normaliza a token YY_MM_DD.
  • Si no se detecta una fecha valida en ninguna fuente, el registro queda para revision y no se marca como listo.
  • Los archivos con patron DW o 1001-03-T-CS pueden prepararse si tienen fecha explicita en el diccionario y cruce espacial valido.

Sector geografico

  • El sector no se infiere desde el nombre del archivo.
  • El sector se toma del cruce espacial con el feature class configurado.
  • Si una imagen cruza dos o mas sectores, se usa el sector con mayor porcentaje de interseccion.
  • El texto del sector se preserva tal como viene desde el feature class; solamente se reemplazan espacios por guion bajo.
  • Si la imagen no cruza ningun sector, el registro queda para revision.

Nombre final

El nombre final se construye con esta estructura:

CL_MLP_PAO_IF_Ortho_YY_MM_DD_Sector.tif

Ejemplo:

CL_MLP_PAO_IF_Ortho_26_05_17_EV2.tif

Duplicados

  • Si dos imagenes generan el mismo nombre final, el notebook agrega una secuencia al final.
  • La secuencia queda antes de la extension: -1, -2, etc.
  • Estos casos siguen pudiendo quedar listos para la etapa siguiente, pero se marcan en review_reason como nombre_duplicado_resuelto.

Carpeta destino

La carpeta de destino se resuelve con un diccionario de sectores validado para el proyecto. Primero se revisan excepciones por nombre original de archivo; si no aplica una excepcion, se usa la regla por sector.

La ruta final queda con esta forma:

\\servidor\CL_MLP_PAO\Carpeta_Drone\YY_MM\CL_MLP_PAO_IF_Ortho_YY_MM_DD_Sector.tif

Diccionarios de nomenclatura

La etapa usa diccionarios simples para transformar el resultado geografico en una ruta de datastore. Estos diccionarios son parte de la configuracion funcional del flujo y deben mantenerse actualizados cuando lleguen nuevos sectores o nuevas excepciones.

Cuando agregar un nuevo sector

Si el cruce espacial encuentra un sector valido pero el manifest queda con review_reason = sin_regla_carpeta_destino, significa que el sector existe en el feature class, pero aun no tiene carpeta destino configurada. En ese caso se debe agregar una entrada nueva al diccionario DESTINATION_FOLDER_BY_SECTOR del notebook.

La nueva entrada debe respetar esta forma:

'Nombre_Sector_Del_Feature': 'Carpeta_Drone_Destino'

Excepciones por nombre original

Antes de aplicar la regla por sector, el flujo revisa un segundo diccionario de excepciones por nombre original de archivo. Este diccionario se usa solo cuando un archivo puntual debe ir a una carpeta distinta a la regla general del sector.

Resultado esperado

Los resultados se escriben siempre en la misma carpeta de salida de la etapa. Cada ejecucion reemplaza los CSV anteriores, para mantener un unico resultado vigente.

flujo_geosupport_etapas\outputs\etapa_01_preparar_paths_datastore
Archivo Contenido Uso recomendado
00_summary.csv Resumen de ejecucion, parametros, totales y estados principales. Validar rapidamente si la corrida encontro imagenes y cuantos registros quedaron listos.

02_spatial_matches.csv Resultado del cruce espacial por imagen. Revisar sector asignado, porcentaje de interseccion y casos con multiples sectores.

Como interpretar el manifest

Campo Interpretacion
ready_for_datastore True significa que la imagen tiene nombre y destino completos para la siguiente etapa.
review_reason Explica por que conviene revisar el registro. Puede indicar falta de fecha, falta de regla de carpeta, cruce con multiples sectores o nombre duplicado resuelto.
path Ruta original de la imagen dentro del input.
expected_file_name Nombre oficial que deberia tener la imagen en el datastore.
destination_path Ruta completa donde se copiara la imagen en la etapa siguiente.
expected_date_token Fecha detectada desde el nombre original en formato YY_MM_DD.
date_source Indica si la fecha vino del diccionario date_dictionary o del nombre del archivo file_name.
spatial_sector_raw Sector original del feature class, usado como fuente del nombre geografico.
spatial_overlap_pct Porcentaje de interseccion con el sector seleccionado. Sirve para revisar confianza cuando cruza multiples sectores.
duplicate_was_resolved Indica que se agrego una secuencia al nombre final para evitar colision.

Criterio para avanzar

  1. Revisar que 00_summary.csv muestre la cantidad esperada de imagenes TIF/TIFF.
  2. Abrir 04_ready_for_datastore.csv y validar visualmente path, expected_file_name y destination_path.
  3. Revisar 05_review_required.csv. Si tiene registros, decidir si se corrigen reglas o si se excluyen de la siguiente etapa.
  4. Usar 04_ready_for_datastore.csv como entrada de la etapa de copia al datastore.
Esta etapa prepara paths y nombres. La validacion de carga efectiva, actualizacion de atributos del mosaico, normalizacion de imagenes, construccion de footprints y publicacion en APRX pertenecen a etapas posteriores.
